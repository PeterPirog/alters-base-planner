# Optimization model

This document is the normative solver contract for `alters-base-planner`.

The model has two layers:

1. **hard feasibility constraints** — a layout is physically valid or rejected;
2. **one soft objective** — minimize the weighted sum of exact pairwise room travel distances.

Corridors and Elevators are always solver-managed. The player supplies only Base tier and room counts.

---

# 1. Explicit room-port model

Every room type defines explicit logical access ports in `ModuleSpec.ports`.

A port contains:

```text
name
side = LEFT | RIGHT
cell_x
cell_y
```

`cell_x` and `cell_y` are coordinates relative to the room footprint. A normal room exposes:

```text
LEFT  port = leftmost cell on the floor row
RIGHT port = rightmost cell on the floor row
```

For a room of width `W` and height `H`:

```text
LEFT  cell = (0, H-1)
RIGHT cell = (W-1, H-1)
```

The physical boundary used for connection checks is:

```text
LEFT  edge_x = room.x
RIGHT edge_x = room.x + room.width
edge_y       = room.y + port.cell_y
```

Therefore high rooms are entered at their actual floor, not at their centroid or ceiling.

For a 1x1 room both logical ports occupy the same physical cell `(0,0)`, but remain distinct LEFT and RIGHT logical ports. If such a room is used as an intermediate transit room, crossing it still costs its full width, i.e. `1`.

Verified game exceptions may define ports on a different row. Radiation Repulsor currently retains top-row ports and remains non-transit.

# 2. Hard constraints

## H1. Exact module multiplicity

Every room requested in `config/plan.json` must be present exactly in the requested count. Mandatory story/core modules are included automatically.

## H2. Solver ownership of utilities

`corridor`, `corridors`, `elevator` and `elevators` are invalid player configuration keys. Their count and placement are generated by the solver.

## H3. Tier-specific irregular base mask

Every room, Corridor and Elevator must fit inside the selected editable Base I-IV CSV mask:

```text
src/alters_base_planner/data/base-size1.csv
src/alters_base_planner/data/base-size2.csv
src/alters_base_planner/data/base-size3.csv
src/alters_base_planner/data/base-size4.csv
```

CSV semantics:

```text
0 = outside usable base
1 = buildable cell
X = immovable blocked/core cell
```

## H4. Immovable core exclusion

No movable module may overlap an `X` cell.

## H5. No overlap

No grid cell may belong to more than one installed module.

## H6. No unsupported rotation

Published room orientation is preserved unless verified game data explicitly allows rotation.

## H7. Legal direct room-to-room connection

Two rooms connect directly only when explicit ports:

- are on the same `edge_y`,
- have the same boundary `edge_x`,
- have opposite sides (`LEFT` versus `RIGHT`).

Direct room adjacency has distance cost `0`.

## H8. Legal room-to-utility connection

A 2x1 Corridor/Elevator may attach only at the utility anchor immediately outside an explicit port:

```text
LEFT  port anchor = (edge_x - 2, edge_y)
RIGHT port anchor = (edge_x,     edge_y)
```

The anchor and both of its cells must be buildable and unoccupied.

## H9. Corridor rules

A Corridor occupies 2x1 cells, connects horizontally and contributes distance `+1` when traversed.

## H10. Elevator local rules

An Elevator occupies 2x1 cells. Vertical connectivity exists only between immediately adjacent Elevator modules at the same `x` coordinate.

Each traversed Elevator module contributes distance `+1`.

## H11. Continuous vertical Elevator coverage

Let all explicit room-port rows span `Lmin ... Lmax`. If more than one row is used:

1. every row in the span must contain at least one Elevator module;
2. at least one Elevator must therefore exist on every used/intermediate floor;
3. every adjacent pair `(y,y+1)` must share at least one Elevator `x`:

```text
ElevatorX[y] intersection ElevatorX[y+1] != empty
```

A shifted shaft is legal only through a transfer floor that supports the necessary connection.

## H12. Single connected base network

Every installed room must be reachable from the Airlock through legal explicit-port adjacency, Corridors and/or Elevators. Disconnected room islands are forbidden.

## H13. Transit versus terminal modules

A module with `transit_allowed = false` may be a destination but may not be used as an intermediate bridge. Current explicit examples are Rapidium Ark and Radiation Repulsor.

## H14. Utility connectivity

Every generated Corridor and Elevator must belong to the access network. Floating utility islands are invalid.

## H15. Base Mass

Every feasible result persists:

```text
room_mass
utility_mass
total_base_mass
organics_required_for_journey
organics_tank_capacity
capacity_margin
travel_feasible_at_full_tank
```

with:

```text
organics_required_for_journey = total_base_mass
Corridor mass = 2
Elevator mass = 2 per module
```

Mass is not part of primary `F`; lower mass is only a tie-breaker when `F` is equal.

# 3. Usage weights

Every room type receives an accepted default gameplay traffic weight in:

```text
src/alters_base_planner/data/usage_weights.json
```

with:

```text
0.0 <= weight <= 1.0
```

Rooms with weight `0` remain subject to all hard constraints but are excluded from objective pairs.

---

# 4. Exact distance definition

Distance `d(i,j)` is the minimum legal path cost between **explicit ports** of endpoint rooms `i` and `j`.

The endpoint room dimensions do not count. Intermediate transit rooms do.

## D1. Direct endpoint adjacency

If a legal port of A directly meets a legal opposite-side port of B:

```text
d(A,B) = 0
```

regardless of the widths of A and B.

## D2. Corridor

Every Corridor module traversed adds:

```text
+1
```

## D3. Elevator

Every individual Elevator module traversed adds:

```text
+1
```

A four-module stack therefore contributes `4`.

## D4. Intermediate room

If an endpoint-to-endpoint path crosses a transit room C from its LEFT port to RIGHT port or vice versa:

```text
+ width(C)
```

For:

```text
A(4x1) | C(6x1) | B(8x1)
```

we get:

```text
d(A,C) = 0
d(C,B) = 0
d(A,B) = 6
```

## D5. High rooms

Distance is measured to the room's explicit port row. For standard high rooms that row is the floor (`H-1` relative to the footprint), so a route cannot enter through the ceiling. Any verified exception must be represented explicitly in the module's port definitions.

# 5. Modified Manhattan lower bound

The solver also calculates an admissible modified Manhattan lower bound between explicit room ports.

For ports on the same floor:

```text
horizontal_lb = ceil(abs(edge_x_a - edge_x_b) / 2)
```

because one 2x1 Corridor spans two horizontal grid cells for distance cost `1`.

For ports on different floors, the solver compares their external 2x1 utility anchors:

```text
horizontal_lb = ceil(abs(anchor_x_a - anchor_x_b) / 2)
vertical_lb   = abs(edge_y_a - edge_y_b) + 1
port_lb       = horizontal_lb + vertical_lb
```

The `+1` reflects the fact that a vertical trip requires Elevator modules on both departure and arrival floors. Using utility anchors prevents double-counting the two-cell Elevator width as an extra horizontal movement.

For a room pair, the minimum bound over all legal port pairs is used:

```text
LB(i,j) = min(port_lb)
```

and the weighted Base lower bound is:

```text
F_LB = sum_{i<j} w(i) * w(j) * LB(i,j)
```

This bound is used for pruning only. The final objective always uses exact legal graph distance. A packing can be skipped when:

```text
F_LB > best_exact_F
```

because it cannot beat the current best solution.

---

# 6. Objective function

Create all unordered pairs of installed rooms with positive usage weight. Corridors, Elevators and rooms with weight `0` do not form objective pairs.

For every pair `(i,j)`:

```text
pair_score(i,j) = weight(i) * weight(j) * d(i,j)
```

and:

```text
F = sum_{i<j} weight(i) * weight(j) * d(i,j)
```

The preferred hard-feasible layout has the smallest exact `F`.

```text

```

For auditing:

```text
F = sum(pairwise_contributions.values())
modified_manhattan_lower_bound <= F
```

# 8. Current implementation and exact-solver target

The current engine:

1. enumerates legal room placements with CP-SAT;
2. resolves explicit room ports;
3. computes the weighted modified-Manhattan lower bound;
4. prunes packings that cannot beat the current exact best score;
5. generates Corridors/Elevators automatically;
6. validates port connectivity and continuous vertical Elevator coverage;
7. computes exact shortest paths through the legal module graph;
8. evaluates exact `F` and retains the best examined candidate;
9. persists Base Mass, ports and journey metrics.

The current placement + post-router architecture does **not yet prove** global optimality over the complete joint room + Corridor + Elevator search space. Only a future integrated exact model may set:

```text
global_objective_optimum_proven = true
```
